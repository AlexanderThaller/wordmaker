== Summary

The download only sets a connect timeout. Decompression is unbounded, and
`open_readfile` then loads the whole file into memory. There is no checksum
(only HTTPS and a database-type check), no fsync before the rename, and a
fixed `.partial` name.

== Location

* `src/analytics/download.rs:349`
* `src/analytics/download.rs:401-411`
* `src/analytics/download.rs:425`

== Impact

* A stalled transfer hangs a cron run forever.
* A crash after rename can leave a truncated database.
* Two overlapping runs write the same `.partial` file.

== Suggested fix

* Add an overall or read timeout and a cap on decompressed size.
* fsync the file and directory before and after the rename.
* Use a unique temporary name.
* Verify the published SHA-256 when available.

== Resolution

* The HTTP client has a 60 s read timeout and a 30 min overall timeout
  besides the connect timeout, so a stalled transfer fails.
* Decompression goes through a writer that fails beyond 1 GiB (the city
  database is about 130 MB), which also bounds what `open_readfile` loads.
* The unpacked file is fsynced before the rename and the directory after.
* The temporary file has a unique name (`<name>.mmdb.<uuid>.partial`,
  created with `create_new`), so overlapping runs do not share it.
* Not done: SHA-256 verification. DB-IP publishes no machine-readable
  checksum next to the `.mmdb.gz` files, so integrity still rests on HTTPS
  and the database type check.
* Checked by downloading both current DB-IP Lite databases.
