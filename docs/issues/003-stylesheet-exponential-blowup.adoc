= 003: Nested block styles make the stylesheet grow exponentially
:severity: High
:area: Themes
:status: fixed
:found: 2026-10-24

[horizontal]
Severity:: High
Area:: Themes
Status:: Fixed

== Summary

`descend()` takes the cross product of the scope selectors and the inner
selectors. `core/heading` and the `heading`/`caption` elements expand to six
selectors each, so every level of nesting multiplies the output by about 7.
The cache has no in-flight deduplication, so each concurrent request starts
its own build.

== Location

* `src/theme/css.rs:533-573`
* `src/theme/css.rs:748-755`
* `src/theme/mod.rs:619-638`

== Impact

* Nesting `+{"blocks":{"core/heading":{"blocks":{"core/heading":...}}}}+`:
  depth 6 gave 0.9 MB, depth 7 gave 6 MB, depth 8 gave 42 MB (measured).
  Depth 12, a `theme.json` of about 300 bytes, is around 100 GB.
* The stylesheet is built on page requests until cached. Concurrent
  requests each spawn a blocking build, leading to OOM or a saturated
  blocking pool: the public site stops serving.
* Second, quadratic variant: `+{"ref":"styles"}+` serialises the whole
  `styles` object at each use. 200 refs turned 8.9 KB of input into 1.8 MB.

== Suggested fix

* Cap nesting depth (WordPress only nests one level), selector count and
  total output size; fail the build with an error when exceeded.
* Reject a `ref` whose target is an object.
* Make builds single-flight per cache key.

== Resolution

* `css::compile` now fails with an error when blocks and elements nest more
  than four levels deep (`WordPress` uses three at most), when one rule
  would get more than 500 selectors, or when the stylesheet grows past
  4 MiB. The size is checked as rules are written, so a build stops early
  rather than after allocating the whole output. A theme that hits a limit
  is logged and the built-in theme is used.
* A `ref` whose target is an object or an array resolves to `initial`
  instead of serialising the target, as `WordPress` ignores such
  references. This also covers references to references.
* `ThemeCache` holds a build lock for the whole build: requests that miss
  the cache at the same time wait for the first build and then share its
  result. The blocking task keeps the lock and stores the result itself,
  so a request that is cancelled mid-build does not let another build
  start.
