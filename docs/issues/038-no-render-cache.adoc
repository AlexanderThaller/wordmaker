= 038: Every public request re-renders AsciiDoc and the footer
:severity: Low
:area: Site rendering
:status: fixed
:found: 2026-10-24

[horizontal]
Severity:: Low
Area:: Site rendering
Status:: Fixed

== Summary

Every GET, 404s included, reparses and highlights the page body and
re-renders the footer AsciiDoc.

== Location

* `src/site.rs:163-180`
* `src/site.rs:332-340`

== Impact

A 180 KB highlighted page took about 250 ms of CPU per request. Authors
control content, so this is a cost and DoS-amplification concern rather
than a vulnerability.

== Suggested fix

* Cache rendered HTML keyed by page id, `updated_at` and settings version.
* Look the page up before building the frame, so 404s are cheap.

== Resolution

`site::RenderCache` (in `AppState::renders`) keeps rendered page bodies,
with images already rewritten, and the rendered footer. It is keyed by a
SHA-256 of what the HTML is made from, not by page id and `updated_at`:
the body plus the theme's content and wide widths for pages, the footer
text for the footer. An edit, a restored revision, a published draft, a
new footer or a theme with other widths therefore misses by itself, with
no invalidation to forget. Title, navigation, settings and the
stylesheet are still read for every request; they are cheap, and the
stylesheet has its own cache. Previews are never cached.

The cache is bounded at 512 entries and 64 MiB, evicts the least
recently used entry, and skips any single entry over 8 MiB.

A page URL now looks the page up before building the frame, so a 404
costs one query. `/` reads the settings once and reuses them for the
frame.

The page key also includes a generation counter from `Images`, bumped when
an image turns out not to be scalable, so cached pages stop offering its
`srcset`. Only problems with the image itself mark it so; I/O failures
such as a full disk do not.
