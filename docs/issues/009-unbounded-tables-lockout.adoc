Severity:: Medium

== Summary

Two tables have a hard cap and refuse new entries when full instead of
evicting old ones.

== Location

* `src/oauth/mod.rs:78`
* `src/oauth/mod.rs:230-236`
* `src/oauth/store.rs:33`
* `crates/wordmaker-admin/src/auth.rs:103`
* `crates/wordmaker-admin/src/auth.rs:478-488`

== Impact

* *Dynamic client registration:* 500 anonymous `POST /oauth/register`
  calls fill `oauth_clients`. Rows never expire (`created_at` is unused), so
  all later registrations fail with "too many registered clients" until
  the database is edited by hand. Count-then-insert is not atomic either,
  so concurrent calls can overshoot 500.
* *Admin sign-in:* every `GET /auth/login` adds a pending-login entry. With
  1000 entries younger than 10 minutes every sign-in gets a 503. About 2
  requests per second keep legitimate users out indefinitely; existing
  sessions are unaffected.

== Suggested fix

* Expire clients that never received a grant (e.g. after 24 h), or evict
  the oldest such client; rate-limit registration per IP.
* Keep no server-side state before the OIDC callback: put the PKCE verifier
  and nonce in a signed or encrypted login cookie. Or evict the oldest entry
  and cap entries per client IP.

== Resolution

*Dynamic client registration:* registered clients record when they
first got tokens (`oauth_clients.used_at`, migration `0005_oauth_reuse.sql`,
backfilled from existing tokens). Registration runs in one transaction that
starts with a write. It drops clients that never got tokens, have no
pending code and are older than 24 hours. When the table is still full,
the oldest such unused clients make way, and the insert itself is
conditional on the count. Registration now fails only when all 500 clients
are in use, which needs 500 approvals with the admin token. Per-IP rate
limiting was not added; see 030 for why.

*Admin sign-in:* `wordmaker-admin` keeps no state for a sign-in under way
any more. The pending-login table and `MAX_PENDING_LOGINS` are gone:
`/auth/login` puts the PKCE verifier, the nonce and the start time into a
login cookie, HMAC-SHA256-signed together with the `state` under a key made
at start-up. The callback checks the MAC and the 10-minute lifetime and
uses the provider as currently discovered. Any number of anonymous
`/auth/login` requests therefore fill nothing and cannot lock anyone out.
