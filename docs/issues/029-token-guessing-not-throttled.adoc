= 029: Wrong-token delay does not limit guessing; /api and /mcp have no delay
:severity: Low
:area: Auth
:status: fixed
:found: 2026-10-24

[horizontal]
Severity:: Low
Area:: Auth
Status:: Fixed

== Summary

The OAuth sign-in sleeps 1 s per failed attempt, but per request, so
parallel attempts are not throttled. `/api` and `/mcp` check the same token
with no delay at all.

== Location

* `src/oauth/mod.rs:408-410`
* `src/app.rs:108-121`
* `src/app.rs:125-143`

== Impact

Tokens from `wordmaker token` have about 244 bits of randomness and are
safe. A weak, hand-chosen `WORDMAKER_TOKEN` can be brute-forced.

== Suggested fix

* Add a global or per-IP failure limiter on all three endpoints.
* Enforce a minimum token length at startup.

== Resolution

* `token::Guesses`, shared through `AppState`, counts wrong admin tokens
  per client address (the connection's peer; IPv6 by /64). After 20 in a
  row, `/api`, `/mcp` and the OAuth sign-in stop checking tokens from that
  address and answer 429 (the sign-in page says so). The allowance comes
  back at one per second. Because the check is refused rather than delayed,
  parallel requests do not help. Valid OAuth access tokens on `/mcp` are
  still accepted while an address is throttled, so signed-in MCP clients
  keep working while someone guesses. Behind a reverse proxy every client has
  the proxy's address and shares one allowance; this is documented in
  README.adoc. More than 10,000 tracked addresses fall back to one shared
  allowance.
* `serve` refuses tokens shorter than 32 characters (`wordmaker token`
  prints 64). A test checks that generated tokens pass.
