= WordMaker

A small CMS written in Rust. Pages are written in AsciiDoc, stored in SQLite and served as a plain website.
Everything can be managed through a REST API or an MCP server, so Claude can write and publish pages for you.

== Running

Requires Rust 1.96 or newer.

[source,sh]
----
cargo build --release
export WORDMAKER_TOKEN=$(./target/release/wordmaker token)
./target/release/wordmaker serve
----

The site is now at http://127.0.0.1:3000.

=== Configuration

[cols="1,1,2"]
|===
|Environment variable |Default |Meaning

|`WORDMAKER_DB` |`sqlite://wordmaker.db` |SQLite database; created and migrated on start
|`WORDMAKER_MEDIA_DIR` |`media` |Where uploaded files are stored
|`WORDMAKER_THEMES_DIR` |`themes` |Where installed themes are stored
|`WORDMAKER_BASE_URL` |`http://127.0.0.1:3000` |Public URL, used for links returned by the API
|`WORDMAKER_MAX_UPLOAD` |`26214400` |Largest upload in bytes
|`WORDMAKER_BIND` |`127.0.0.1:3000` |Listen address (`serve` only)
|`WORDMAKER_TOKEN` |– |Bearer token for `/api` and `/mcp` (required by `serve` and `client`)
|`WORDMAKER_MCP_URL` |`$WORDMAKER_BASE_URL/mcp` |MCP endpoint (`client` only)
|`WORDMAKER_ALLOWED_HOSTS` |– |Extra comma-separated `Host` values accepted by `/mcp`
|===

Every variable also has a command line flag, see `wordmaker --help`.

== Admin interface

`wordmaker-admin` is a web interface for a running server: write pages in a WYSIWYG AsciiDoc editor (https://www.npmjs.com/package/asciidoc-editor[asciidoc-editor]) with a live preview in the site's theme, publish them, browse their history and restore old revisions, upload media, and change the site settings and theme.

Changes to a published page are saved as a draft: the site keeps showing the published version until you press _Publish changes_, and _Discard changes_ throws the draft away.
Slug and navigation settings are not drafted and change at once.

[source,sh]
----
cargo build --release --workspace
WORDMAKER_TOKEN=... ./target/release/wordmaker-admin
----

Then open http://127.0.0.1:3001.
It talks to the server at `WORDMAKER_BASE_URL` through the REST API and holds the token itself, so the browser never sees it.
That also means anyone who can reach the interface can change the site: it listens on `127.0.0.1:3001` (`WORDMAKER_ADMIN_BIND`) and only answers to loopback host names.
To reach it under another name, behind something that checks who is asking, add the name to `WORDMAKER_ADMIN_ALLOWED_HOSTS`.

The editor is vendored in `crates/wordmaker-admin/vendor`; `vendor/update-editor.sh [version]` replaces it with a release from npm.

== Claude Desktop

=== Local (stdio)

Claude Desktop starts WordMaker itself. Add this to `claude_desktop_config.json` and point it at the same database as the web server:

[source,json]
----
{
  "mcpServers": {
    "wordmaker": {
      "command": "/path/to/wordmaker",
      "args": ["mcp"],
      "env": {
        "WORDMAKER_DB": "sqlite:///path/to/wordmaker.db",
        "WORDMAKER_MEDIA_DIR": "/path/to/media",
        "WORDMAKER_THEMES_DIR": "/path/to/themes",
        "WORDMAKER_BASE_URL": "http://127.0.0.1:3000"
      }
    }
  }
}
----

Use absolute paths: Claude Desktop does not start the process in your project directory.
The stdio server needs no token, and does not need `wordmaker serve` to be running, though you will want it running to see the result.

=== Remote (HTTP)

`wordmaker serve` also speaks MCP (streamable HTTP) at `/mcp`, protected by the same bearer token as the API.
Clients that cannot set the `Authorization` header, such as Claude's custom connectors, can send the token as `X-WordMaker-Token: $WORDMAKER_TOKEN` instead (no `Bearer` prefix).
When the server is not reached through `localhost`, set `WORDMAKER_BASE_URL` (or `WORDMAKER_ALLOWED_HOSTS`) to the public host name, otherwise MCP requests are rejected to prevent DNS rebinding.

=== Tools

`list_pages`, `get_page`, `create_page`, `update_page`, `delete_page`, `publish_page`, `unpublish_page`, `save_draft`, `discard_draft`,
`list_revisions`, `get_revision`, `restore_revision`, `preview_adoc`,
`upload_media`, `list_media`, `delete_media`, `get_settings`, `set_settings`,
`list_themes`, `install_theme`, `activate_theme`, `delete_theme`.

=== Command line client

Agents that can run shell commands but have no MCP support can use `wordmaker client`, which talks to the `/mcp` endpoint of a running server.
It reads `WORDMAKER_TOKEN` and connects to `$WORDMAKER_BASE_URL/mcp` (override with `--url` or `WORDMAKER_MCP_URL`).

[source,sh]
----
wordmaker client info                 # server version and usage instructions
wordmaker client tools                # every tool with its parameters
wordmaker client tools create_page    # one tool; add --json for the full schema

wordmaker client call create_page '{"title": "About"}' --file body=about.adoc --json publish=true
wordmaker client call get_page --arg slug=about
wordmaker client call upload_media --arg filename=logo.png --base64 content_base64=logo.png
echo '{"slug": "about"}' | wordmaker client call get_page -
----

Arguments come from an optional JSON object (`-` reads it from stdin), overridden by
`--arg KEY=VALUE` (string), `--json KEY=JSON`, `--file KEY=PATH` (file contents as a string) and `--base64 KEY=PATH`.
The result goes to stdout; a failed tool call prints the error to stderr and exits with status 1.

== REST API

All endpoints live under `/api/v1` and require `Authorization: Bearer $WORDMAKER_TOKEN` (or `X-WordMaker-Token: $WORDMAKER_TOKEN`).

[cols="1,2"]
|===
|Endpoint |Purpose

|`GET /pages?status=draft\|published` |List pages
|`POST /pages` |Create: `{"title", "slug"?, "body"?, "publish"?}`
|`GET /pages/{slug}` |Page with AsciiDoc body
|`PATCH /pages/{slug}` |Change `title`, `slug`, `body`, `in_nav` and/or `nav_order`
|`DELETE /pages/{slug}` |Delete page and its history
|`POST /pages/{slug}/publish`, `/unpublish` |Change visibility; publishing makes a pending draft live
|`PUT /pages/{slug}/draft` |Keep changes to `title` and/or `body` without publishing them
|`DELETE /pages/{slug}/draft` |Throw the pending draft away
|`GET /pages/{slug}/revisions` |Revision list, newest first
|`GET /pages/{slug}/revisions/{n}` |One revision
|`POST /pages/{slug}/revisions/{n}/restore` |Make a revision current again
|`POST /render` |Render `{"body"}` to HTML without saving
|`POST /preview` |The whole page, in the site's frame and theme, for `{"title", "slug"?, "body"}`, without saving
|`GET /media`, `POST /media` (multipart), `DELETE /media/{filename}` |Uploaded files
|`GET /settings`, `PUT /settings` |`site_title`, `site_tagline`, `footer_text`, `home_slug`
|`GET /themes` |Installed themes and their style variations
|`POST /themes/install` |Install from `{"wordpress_org": "twentytwentyfive", "version"?}` or `{"url"}`
|`POST /themes/upload?slug=` |Install from a zip sent as the request body
|`PUT /themes/active` |Activate `{"theme", "variations": [...]}`; `{"theme": null}` for the built-in look
|`DELETE /themes/{slug}` |Remove a theme that is not active
|===

[source,sh]
----
curl -H "Authorization: Bearer $WORDMAKER_TOKEN" -H 'content-type: application/json' \
  -d '{"title": "About", "body": "== Who we are\n\nHello!", "publish": true}' \
  http://127.0.0.1:3000/api/v1/pages
----

== Writing pages

* The page title is rendered as the heading, so start the body with `==` sections rather than a `= Title` line.
* Reference uploaded images by their path: `image::/media/1a2b3c4d-logo.png[Logo]`.
* Link to other pages with `link:/about[About]`.
* Changing a published page with `PATCH` changes the site at once.
To prepare changes first, save them as a draft (`PUT /pages/{slug}/draft`): the site keeps showing the published version until the page is published again, which makes the draft live as a new revision.
* Only published pages are visible on the site. `/` shows the page chosen as `home_slug`, or a list of all published pages.
* Published pages appear in the header navigation, ordered by `nav_order` then title; set `in_nav` to false to leave one out.

== Themes

WordMaker can use the design of WordPress *block themes*, the ones with a `theme.json`, such as Twenty Twenty-Five:

[source,sh]
----
curl -H "Authorization: Bearer $WORDMAKER_TOKEN" -H 'content-type: application/json' \
  -d '{"wordpress_org": "twentytwentyfive", "version": "1.5"}' http://127.0.0.1:3000/api/v1/themes/install
curl -X PUT -H "Authorization: Bearer $WORDMAKER_TOKEN" -H 'content-type: application/json' \
  -d '{"theme": "twentytwentyfive", "variations": ["01-evening"]}' http://127.0.0.1:3000/api/v1/themes/active
----

Or just ask Claude: "install Twenty Twenty-Five and use the Evening style".

=== What is used

`theme.json` is compiled into the same CSS WordPress generates:

* Presets: palette, gradients, font sizes (including fluid sizes), font families, spacing, shadows and `custom` values, as `--wp--preset--*` and `--wp--custom--*` properties, plus the `has-*-color`, `has-*-background-color`, `has-*-font-size` classes.
* The fonts bundled with the theme (`fontFace`), served from the theme folder.
* Layout: content and wide sizes, root padding, block gap.
* Styles for the body, elements (links, headings, buttons, captions) and blocks. Blocks that have an AsciiDoc counterpart (paragraph, list, code, quote, separator, table, image) style that too.
* Style variations from `styles/`, combinable, e.g. a `colors/…` and a `typography/…` preset.
* Section and block styles (`styles/sections`, `styles/blocks`) as `is-style-*` classes.
* The theme's `style.css`.

Templates, template parts and PHP patterns are *not* used, and PHP files are not even unpacked.
Pages use WordMaker's own frame, laid out like Twenty Twenty-Five's page template with WordPress's class names: a header with site title and navigation, the title and content in the content width, and a footer with site title, tagline and footer text.

=== Using theme styles in AsciiDoc

[source,asciidoc]
----
[.has-accent-3-color]#Text in a palette color#

[.alignwide]
image::/media/1a2b3c4d-hero.jpg[Hero]

[.is-style-section-1.alignfull]
--
[discrete]
=== A highlighted section

Content on the theme's section background.
--
----

Columns work like WordPress's columns block: an open block with the `wp-block-columns` role holds one example block with the `wp-block-column` role per column.
They sit side by side from 782px and stack on narrower screens (add `is-not-stacked-on-mobile` to keep them side by side); `are-vertically-aligned-center` (or `-top`, `-bottom`) aligns them.

[source,asciidoc]
----
[.wp-block-columns.are-vertically-aligned-center]
--
[.wp-block-column]
====
[discrete]
== About me

A paragraph next to the photo.
====

[.wp-block-column]
====
image::/media/1a2b3c4d-portrait.jpg[Portrait]
====
--
----

Without a theme, WordMaker uses a built-in look that follows the reader's light or dark preference.
