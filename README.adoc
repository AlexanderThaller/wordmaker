= WordMaker

A small CMS written in Rust. Pages are written in AsciiDoc, stored in SQLite and served as a plain website.
Everything can be managed through a REST API or an MCP server, so Claude can write and publish pages for you.

== Running

Requires Rust 1.96 or newer.

[source,sh]
----
cargo build --release
export WORDMAKER_TOKEN=$(./target/release/wordmaker token)
./target/release/wordmaker serve
----

The site is now at http://127.0.0.1:3000.

=== Configuration

[cols="1,1,2"]
|===
|Environment variable |Default |Meaning

|`WORDMAKER_DB` |`sqlite://wordmaker.db` |SQLite database; created and migrated on start
|`WORDMAKER_MEDIA_DIR` |`media` |Where uploaded files are stored
|`WORDMAKER_THEMES_DIR` |`themes` |Where installed themes are stored
|`WORDMAKER_BASE_URL` |`http://127.0.0.1:3000` |Public URL, used for links returned by the API
|`WORDMAKER_MAX_UPLOAD` |`26214400` |Largest upload in bytes
|`WORDMAKER_BIND` |`127.0.0.1:3000` |Listen address (`serve` only)
|`WORDMAKER_TOKEN` |– |Bearer token for `/api` and `/mcp` (required by `serve`, `client` and `wordmaker-admin`)
|`WORDMAKER_TOKEN_FILE` |– |File holding the token instead, e.g. a systemd credential (`$CREDENTIALS_DIRECTORY/token`) or Docker secret; surrounding whitespace is ignored
|`WORDMAKER_MCP_URL` |`$WORDMAKER_BASE_URL/mcp` |MCP endpoint (`client` only)
|`WORDMAKER_ALLOWED_HOSTS` |– |Extra comma-separated `Host` values accepted by `/mcp`
|`WORDMAKER_CLICKHOUSE_URL` |– |ClickHouse HTTP endpoint for page-view analytics, e.g. `http://127.0.0.1:8123`; analytics is off without it
|`WORDMAKER_CLICKHOUSE_DATABASE` |`wordmaker` |ClickHouse database; must exist, the `page_views` table is created on start
|`WORDMAKER_CLICKHOUSE_USER` |`default` |ClickHouse user
|`WORDMAKER_CLICKHOUSE_PASSWORD` |– |ClickHouse password
|`WORDMAKER_CLICKHOUSE_PASSWORD_FILE` |– |File holding the ClickHouse password instead
|`WORDMAKER_GEOIP_CITY_DB` |– |MaxMind GeoLite2-City `.mmdb` for country, region and city
|`WORDMAKER_GEOIP_ASN_DB` |– |MaxMind GeoLite2-ASN `.mmdb` for the visitor's network
|`WORDMAKER_PROXY_HOPS` |`1` |Reverse proxies appending to `X-Forwarded-For`; `0` uses the connection's address
|`WORDMAKER_GEOIP_DIR` |`geoip` |Where `wordmaker geoip` saves the DB-IP databases
|===

Every variable also has a command line flag, see `wordmaker --help`.

=== Analytics

With `WORDMAKER_CLICKHOUSE_URL` set, `serve` records every `GET` of `/` and of a page (including 404s) in the ClickHouse table `page_views`.
Assets, media, the API and MCP are not recorded.
Any number of instances can share one database: the `site` column holds each instance's `WORDMAKER_BASE_URL`.

[source,sql]
----
CREATE DATABASE wordmaker;
----

Each row has the path and slug, status and render time, referrer and its host, `utm_source`/`utm_medium`/`utm_campaign`, the user agent with browser, OS, device type and a bot flag (crawlers the parser knows, plus anything calling itself a bot, crawler or spider, headless browsers included), the preferred language, and, with the GeoIP databases, country, region, city and network (ASN).
`wordmaker geoip` downloads the free https://db-ip.com/db/lite.php[DB-IP Lite] city and ASN databases (no account needed) into `WORDMAKER_GEOIP_DIR` and prints the settings that point at them; DB-IP publishes a new edition every month.
MaxMind's GeoLite2 files work as well, kept current with https://github.com/maxmind/geoipupdate[geoipupdate].
A running `serve` checks the files every minute and loads new versions by itself; if a new file cannot be opened, it keeps using the old one.
The databases are memory-mapped rather than read into memory, so only the parts lookups touch take up RAM, as page cache the system can reclaim.
That is why a database file must never be changed in place while `serve` runs: replace it by renaming a new file over it, as `wordmaker geoip` and `geoipupdate` do (`cp` straight onto it could crash the server).
The DB-IP Lite data is licensed under https://creativecommons.org/licenses/by/4.0/[CC BY 4.0]; credit it as "IP Geolocation by DB-IP" wherever you show results based on it.

[source,sh]
----
wordmaker geoip --dir /var/lib/wordmaker/geoip   # e.g. monthly from a systemd timer or cron
----

No IP address is stored.
The address is used for the GeoIP lookup and for `visitor_id`, a hash of address and user agent with a random salt that only lives in memory and changes every UTC day.
It counts unique visitors per day, but cannot be traced back to an address or followed across days.

Analytics never slows the site down: requests only queue a page view, without waiting.
When ClickHouse is unreachable, page views are buffered (up to 50,000) and written once it is back.
On shutdown (Ctrl-C or SIGTERM) the buffer is written before the process exits.

[source,sql]
----
-- Views and unique visitors per site and day, without bots
SELECT site, toDate(timestamp) AS day, count() AS views, uniq(visitor_id) AS visitors
FROM page_views WHERE NOT is_bot AND status = 200
GROUP BY site, day ORDER BY day DESC, site;

-- Top pages and countries this month
SELECT site, path, country, count() AS views
FROM page_views WHERE NOT is_bot AND timestamp >= toStartOfMonth(now())
GROUP BY site, path, country ORDER BY views DESC LIMIT 20;
----

`cargo test` also writes page views to a real ClickHouse it starts in Docker (with https://crates.io/crates/testcontainers[testcontainers]); without Docker that test is skipped.

=== Grafana

`grafana/wordmaker.json` is a Grafana dashboard for all instances writing to one database: the totals, page views over time per site, a table of the sites, a map and the same top lists as the admin dashboard.
The _Site_ selector shows all instances or the ones you pick; clicking a site in the _Sites_ table shows only that one.

It needs Grafana 11 or newer with the https://grafana.com/grafana/plugins/grafana-clickhouse-datasource/[ClickHouse data source] plugin.
Add a ClickHouse data source for the server (HTTP, port 8123), then import the file under _Dashboards → New → Import_ and pick the data source.
If the database is not called `wordmaker`, change the _Database_ field at the top.
To provision it instead, point a dashboard provider at the `grafana` directory:

[source,yaml]
----
apiVersion: 1
providers:
  - name: wordmaker
    type: file
    options:
      path: /path/to/wordmaker/grafana
----

== Admin interface

`wordmaker-admin` is a web interface for a running server: write pages in a WYSIWYG AsciiDoc editor (https://www.npmjs.com/package/asciidoc-editor[asciidoc-editor]) with a live preview in the site's theme, publish them, browse their history and restore old revisions, upload media, change the site settings and theme, and see the page-view dashboard when analytics is on; it can refresh itself every 10 seconds to 15 minutes while it is in view.

Changes to a published page are saved as a draft: the site keeps showing the published version until you press _Publish changes_, and _Discard changes_ throws the draft away.
Slug and navigation settings are not drafted and change at once.

[source,sh]
----
cargo build --release --workspace
WORDMAKER_TOKEN_FILE=/path/to/token ./target/release/wordmaker-admin
----

Then open http://127.0.0.1:3001.
It talks to the server at `WORDMAKER_BASE_URL` through the REST API and holds the token itself, so the browser never sees it.
When that is an internal address, set `WORDMAKER_ADMIN_SITE_URL` to the site's public URL for the interface's links to the site.
That also means anyone who can reach the interface can change the site: it listens on `127.0.0.1:3001` (`WORDMAKER_ADMIN_BIND`) and only answers to loopback host names.
To reach it under another name, behind something that checks who is asking, add the name to `WORDMAKER_ADMIN_ALLOWED_HOSTS`.

Or let it check itself: with `WORDMAKER_ADMIN_OIDC_ISSUER` set, people sign in through an OpenID Connect provider (Keycloak, Authentik, Google, GitLab, …) before they see anything.

[source,sh]
----
WORDMAKER_ADMIN_BIND=0.0.0.0:3001 \
WORDMAKER_ADMIN_PUBLIC_URL=https://admin.example \
WORDMAKER_ADMIN_OIDC_ISSUER=https://keycloak.example/realms/main \
WORDMAKER_ADMIN_OIDC_CLIENT_ID=wordmaker-admin \
WORDMAKER_ADMIN_OIDC_CLIENT_SECRET_FILE=/path/to/client-secret \
WORDMAKER_ADMIN_ALLOWED_USERS=alice@example.com,@team.example \
WORDMAKER_TOKEN_FILE=/path/to/token ./target/release/wordmaker-admin
----

Register `<public URL>/auth/callback` as the redirect URI with the provider; the public URL's host is answered to as well.
Only verified email addresses on `WORDMAKER_ADMIN_ALLOWED_USERS` get in, either exactly or by `@domain`.
The client secret is optional for providers that register public clients, since the sign-in uses PKCE.
Sessions last 12 hours and are kept in memory, so a restart signs everyone out.

The editor is vendored in `crates/wordmaker-admin/vendor`; `vendor/update-editor.sh [version integrity]` replaces it with a release from npm, checked against the sha512 integrity hash pinned in the script.
The dashboard's world map is generated from https://www.naturalearthdata.com/[Natural Earth] (public domain) by `vendor/update-world.sh`.

== Claude Desktop

=== Local (stdio)

Claude Desktop starts WordMaker itself. Add this to `claude_desktop_config.json` and point it at the same database as the web server:

[source,json]
----
{
  "mcpServers": {
    "wordmaker": {
      "command": "/path/to/wordmaker",
      "args": ["mcp"],
      "env": {
        "WORDMAKER_DB": "sqlite:///path/to/wordmaker.db",
        "WORDMAKER_MEDIA_DIR": "/path/to/media",
        "WORDMAKER_THEMES_DIR": "/path/to/themes",
        "WORDMAKER_BASE_URL": "http://127.0.0.1:3000"
      }
    }
  }
}
----

Use absolute paths: Claude Desktop does not start the process in your project directory.
The stdio server needs no token, and does not need `wordmaker serve` to be running, though you will want it running to see the result.

=== Remote (HTTP)

`wordmaker serve` also speaks MCP (streamable HTTP) at `/mcp`, protected by the same bearer token as the API.
Clients that cannot set the `Authorization` header can send the token as `X-WordMaker-Token: $WORDMAKER_TOKEN` instead (no `Bearer` prefix).

==== OAuth

`/mcp` also supports OAuth as described by the MCP authorization spec, so clients such as Claude's custom connectors only need the URL, `https://example.com/mcp`.
On first use the client opens a sign-in page on your site; enter `WORDMAKER_TOKEN` there and approve.
The client then gets an access token (valid for an hour) and a refresh token (30 days, renewed on every use).

* `WORDMAKER_BASE_URL` must be the public URL the client connects to, e.g. `https://example.com`; it is the OAuth issuer and part of every metadata URL.
* Clients identify themselves with a client ID metadata document or through dynamic client registration.
* OAuth tokens are only accepted on `/mcp`, not on `/api`.
* Changing `WORDMAKER_TOKEN` signs out every OAuth client.

Endpoints: `/.well-known/oauth-protected-resource[/mcp]`, `/.well-known/oauth-authorization-server`,
`/oauth/authorize`, `/oauth/token`, `/oauth/register`, `/oauth/revoke`.
When the server is not reached through `localhost`, set `WORDMAKER_BASE_URL` (or `WORDMAKER_ALLOWED_HOSTS`) to the public host name, otherwise MCP requests are rejected to prevent DNS rebinding.

=== Command line client

Agents that can run shell commands but have no MCP support can use `wordmaker client`, which talks to the `/mcp` endpoint of a running server.
It reads `WORDMAKER_TOKEN` (or `WORDMAKER_TOKEN_FILE`) and connects to `$WORDMAKER_BASE_URL/mcp` (override with `--url` or `WORDMAKER_MCP_URL`).

[source,sh]
----
wordmaker client info                 # server version and usage instructions
wordmaker client tools                # every tool with its parameters
wordmaker client tools create_page    # one tool; add --json for the full schema

wordmaker client call create_page '{"title": "About"}' --file body=about.adoc --json publish=true
wordmaker client call get_page --arg slug=about
wordmaker client call upload_media --arg filename=logo.png --base64 content_base64=logo.png
echo '{"slug": "about"}' | wordmaker client call get_page -
----

Arguments come from an optional JSON object (`-` reads it from stdin), overridden by
`--arg KEY=VALUE` (string), `--json KEY=JSON`, `--file KEY=PATH` (file contents as a string) and `--base64 KEY=PATH`.
The result goes to stdout; a failed tool call prints the error to stderr and exits with status 1.

== REST API

All endpoints live under `/api/v1` and require `Authorization: Bearer $WORDMAKER_TOKEN` (or `X-WordMaker-Token: $WORDMAKER_TOKEN`).

[cols="1,2"]
|===
|Endpoint |Purpose

|`GET /pages?status=draft\|published` |List pages
|`POST /pages` |Create: `{"title", "slug"?, "body"?, "publish"?}`
|`GET /pages/{slug}` |Page with AsciiDoc body
|`PATCH /pages/{slug}` |Change `title`, `slug`, `body`, `in_nav` and/or `nav_order`
|`DELETE /pages/{slug}` |Delete page and its history
|`POST /pages/{slug}/publish`, `/unpublish` |Change visibility; publishing makes a pending draft live
|`PUT /pages/{slug}/draft` |Keep changes to `title` and/or `body` without publishing them
|`DELETE /pages/{slug}/draft` |Throw the pending draft away
|`GET /pages/{slug}/revisions` |Revision list, newest first
|`GET /pages/{slug}/revisions/{n}` |One revision
|`POST /pages/{slug}/revisions/{n}/restore` |Make a revision current again
|`POST /render` |Render `{"body"}` to HTML without saving
|`POST /preview` |The whole page, in the site's frame and theme, for `{"title", "slug"?, "body"}`, without saving
|`GET /media`, `POST /media` (multipart), `DELETE /media/{filename}` |Uploaded files
|`GET /settings`, `PUT /settings` |`site_title`, `site_tagline`, `footer_text`, `home_slug`
|`GET /themes` |Installed themes and their style variations
|`POST /themes/install` |Install from `{"wordpress_org": "twentytwentyfive", "version"?}` or `{"url"}`
|`POST /themes/upload?slug=` |Install from a zip sent as the request body
|`PUT /themes/active` |Activate `{"theme", "variations": [...]}`; `{"theme": null}` for the built-in look
|`GET /themes/{slug}` |One theme with the list of its files
|`GET /themes/{slug}/files/{path}`, `PUT /themes/{slug}/files/{path}` |Read or replace a text file of a theme, as `{"content"}`; the site uses a change right away
|`DELETE /themes/{slug}` |Remove a theme that is not active
|`GET /analytics?days=30` |Page-view report for the last 1–366 days: totals, views per day, top pages, referrers, countries, browsers, systems, devices, 404s, bots by name and views per country code; 404 when analytics is off
|===

[source,sh]
----
curl -H "Authorization: Bearer $WORDMAKER_TOKEN" -H 'content-type: application/json' \
  -d '{"title": "About", "body": "== Who we are\n\nHello!", "publish": true}' \
  http://127.0.0.1:3000/api/v1/pages
----

== Writing pages

* The page title is rendered as the heading, so start the body with `==` sections rather than a `= Title` line.
* Reference uploaded images by their path: `image::/media/1a2b3c4d-logo.png[Logo]`.
* Link to other pages with `link:/about[About]`.
* Changing a published page with `PATCH` changes the site at once.
To prepare changes first, save them as a draft (`PUT /pages/{slug}/draft`): the site keeps showing the published version until the page is published again, which makes the draft live as a new revision.
* Only published pages are visible on the site. `/` shows the page chosen as `home_slug`, or a list of all published pages.
* Published pages appear in the header navigation, ordered by `nav_order` then title; set `in_nav` to false to leave one out.

== Themes

WordMaker can use the design of WordPress *block themes*, the ones with a `theme.json`, such as Twenty Twenty-Five:

[source,sh]
----
curl -H "Authorization: Bearer $WORDMAKER_TOKEN" -H 'content-type: application/json' \
  -d '{"wordpress_org": "twentytwentyfive", "version": "1.5"}' http://127.0.0.1:3000/api/v1/themes/install
curl -X PUT -H "Authorization: Bearer $WORDMAKER_TOKEN" -H 'content-type: application/json' \
  -d '{"theme": "twentytwentyfive", "variations": ["01-evening"]}' http://127.0.0.1:3000/api/v1/themes/active
----

Or just ask Claude: "install Twenty Twenty-Five and use the Evening style".

=== What is used

`theme.json` is compiled into the same CSS WordPress generates:

* Presets: palette, gradients, font sizes (including fluid sizes), font families, spacing, shadows and `custom` values, as `--wp--preset--*` and `--wp--custom--*` properties, plus the `has-*-color`, `has-*-background-color`, `has-*-font-size` classes.
* The fonts bundled with the theme (`fontFace`), served from the theme folder.
* Layout: content and wide sizes, root padding, block gap.
* Styles for the body, elements (links, headings, buttons, captions) and blocks. Blocks that have an AsciiDoc counterpart (paragraph, list, code, quote, separator, table, image) style that too.
* Style variations from `styles/`, combinable, e.g. a `colors/…` and a `typography/…` preset.
* Section and block styles (`styles/sections`, `styles/blocks`) as `is-style-*` classes.
* The theme's `style.css`.

Templates, template parts and PHP patterns are *not* used, and PHP files are not even unpacked.
Pages use WordMaker's own frame, laid out like Twenty Twenty-Five's page template with WordPress's class names: a header with site title and navigation, the title and content in the content width, and a footer with site title, tagline and footer text.

=== Using theme styles in AsciiDoc

[source,asciidoc]
----
[.has-accent-3-color]#Text in a palette color#

[.alignwide]
image::/media/1a2b3c4d-hero.jpg[Hero]

[.is-style-section-1.alignfull]
--
[discrete]
=== A highlighted section

Content on the theme's section background.
--
----

Columns work like WordPress's columns block: an open block with the `wp-block-columns` role holds one example block with the `wp-block-column` role per column.
They sit side by side from 782px and stack on narrower screens (add `is-not-stacked-on-mobile` to keep them side by side); `are-vertically-aligned-center` (or `-top`, `-bottom`) aligns them.

[source,asciidoc]
----
[.wp-block-columns.are-vertically-aligned-center]
--
[.wp-block-column]
====
[discrete]
== About me

A paragraph next to the photo.
====

[.wp-block-column]
====
image::/media/1a2b3c4d-portrait.jpg[Portrait]
====
--
----

Without a theme, WordMaker uses a built-in look that follows the reader's light or dark preference.
